# Стриминг в Iceberg: «каталог в виде .duckdb + version-hint» против REST-каталога

Воспроизводимый стенд на Docker Compose. Он проверяет, как ведут себя читатели DuckDB, когда в таблицу Iceberg постоянно пишут:

- **стриминг:** фиксация раз в 1 секунду;
- **микробатч:** фиксация раз в 10 секунд.

Сравниваются две схемы чтения:

| Схема | Как писатель сообщает о новой версии | Как читатель находит текущую версию |
|---|---|---|
| `hint` — каталог в виде `.duckdb` + hint | Фиксация в локальном SQLite-каталоге писателя (читателям недоступен), затем условная запись (CAS) файла `<таблица>/metadata/version-hint.text` в S3 | Подключает из S3 файл `catalog/<таблица>.duckdb` (`ATTACH … READ_ONLY`). В нём одно представление `events AS SELECT * FROM iceberg_scan('<путь таблицы>')`. Каждый запрос читает `version-hint.text`, по нему находит текущий `metadata.json` |
| `rest` — REST-каталог Iceberg | Фиксация через REST-каталог (`tabulario/iceberg-rest`) | Подключает каталог (`ATTACH … (TYPE iceberg, ENDPOINT …)`). Каждый запрос спрашивает у каталога текущий `metadata.json` |

Данные и метаданные в обеих схемах лежат в одном S3 (MinIO). Писатель и читатели одинаковые: PyIceberg 0.12.0 и DuckDB 1.5.6.

## Как запустить

Нужны Docker и Docker Compose. При первой сборке нужна сеть: образы, пакеты PyPI, расширения DuckDB (`httpfs`, `avro`, `iceberg`) скачиваются на этапе сборки. Сам прогон сеть наружу не использует.

```sh
docker compose up --build --abort-on-container-exit --exit-code-from runner runner
docker compose down -v      # удалить контейнеры и данные MinIO
```

По умолчанию прогон идёт около 26 минут. Сценарии запускаются по очереди, внутри сценария сначала `hint`, затем `rest`:

| Сценарий | Интервал фиксаций | Длительность |
|---|---|---|
| `stream` | 1 с | 180 с |
| `microbatch` | 10 с | 600 с |

Параметры задаются переменными окружения:

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `SCENARIOS` | `stream:1:180,microbatch:10:600` | Список `имя:интервал_с:длительность_с` |
| `VARIANTS` | `hint,rest` | Какие схемы сравнивать |
| `BATCH_ROWS` | `1000` | Строк в одной фиксации |
| `READERS` | `4` | Параллельных читателей; каждый — отдельный процесс с одной долгой сессией DuckDB |
| `READER_PAUSE_S` | `0.2` | Пауза между запросами одного читателя |

Например, короткая проверка стенда:

```sh
SCENARIOS=stream:1:20,microbatch:10:40 docker compose up --build --abort-on-container-exit --exit-code-from runner runner
```

## Что получается на выходе

В папке `results/`:

| Файл | Содержимое |
|---|---|
| `summary.md` | Сводная таблица метрик по всем прогонам (её же печатает runner) и ошибки по видам |
| `summary.json` | Все метрики всех прогонов |
| `<схема>-<сценарий>/metrics.json` | Метрики одного прогона |
| `<схема>-<сценарий>/writer.jsonl` | Сырые события писателя, по строке на фиксацию |
| `<схема>-<сценарий>/reader-N.jsonl` | Сырые события читателя N, по строке на запрос или ошибку |

Каждый прогон пишет в новую таблицу. Прогоны не мешают друг другу и не используют данные прошлых запусков.

## Как устроен прогон

1. Писатель (`bench/writer.py`) создаёт таблицу из четырёх колонок: `seq`, `batch`, `written_at`, `payload`.
2. Каждые `интервал` секунд писатель добавляет (`append`) пакет из `BATCH_ROWS` строк. Номера `seq` идут подряд без пропусков: 1…1000, 1001…2000 и так далее. Значит, после *k* фиксаций в таблице ровно `k × BATCH_ROWS` строк, и `max(seq)` равен их числу.
3. В схеме `hint` после каждой фиксации писатель публикует `version-hint.text` (условный PUT с `If-Match` по ETag).
4. После первой фиксации runner для схемы `hint` создаёт файл каталога `.duckdb` с представлением и кладёт его в S3. Затем запускает читателей.
5. Каждый читатель (`bench/reader.py`) держит одну сессию DuckDB и в цикле выполняет:
   ```sql
   SELECT max(seq), count(*), count(DISTINCT seq) FROM <таблица>
   ```
6. Все процессы работают в одном контейнере, поэтому у писателя и читателей одни часы. Времена событий сопоставимы до миллисекунд.
7. `bench/analyze.py` считает метрики по сырым событиям. Списки объектов и размер последнего `metadata.json` он берёт из S3.

## Метрики

Обозначения:
- `t_start` и `t_end` — начало и конец запроса читателя;
- `t_commit` — момент, когда писатель получил подтверждение фиксации;
- `t_visible` — момент, когда новая версия стала доступна читателям. Для `hint` это конец публикации `version-hint.text`, для `rest` он совпадает с `t_commit`.

| Метрика | Как считается | Что значит |
|---|---|---|
| **Фиксаций / снимков в конце** | Число событий `commit` у писателя и число снимков в метаданных после последней фиксации | Сколько версий таблицы накопилось. От этого растут метаданные и время запросов |
| **Запросов читателей** | Число успешных запросов всех читателей | Объём выборки, на котором посчитаны остальные метрики |
| **Ошибок запросов (доля)** | Число запросов, завершившихся исключением, и их доля от всех попыток в процентах. Виды ошибок с текстом перечислены под таблицей | Насколько часто читатель получает ошибку из-за параллельной записи. Ошибка не означает неверные данные: запрос падает явно |
| **Несогласованных результатов** | Число успешных запросов, где `count(*) ≠ max(seq)` или `count(DISTINCT seq) ≠ count(*)` | Главная проверка целостности. Если запрос видит полусобранную версию, то есть часть пакета, дубли или пропуски, равенство нарушается. Ожидается 0 |
| **Возраст данных**, медиана / p95 / max | Для каждого запроса: `t_end − t_commit` той фиксации, которая дала увиденный `max(seq)` | Насколько старые данные видит читатель в момент получения результата. Нижняя граница — около половины интервала фиксаций: в среднем запрос попадает на середину паузы между фиксациями. Всё, что сверх этого, — задержка публикации и чтения |
| **Запросов, пропустивших уже видимый пакет** | Для каждого запроса берётся последний пакет с `t_visible ≤ t_start` (уже был опубликован, когда запрос начался). Если `max(seq)` в результате меньше, запрос «пропустил» пакеты. Показывается доля таких запросов, распределение по числу пропущенных пакетов — в `metrics.json` (`missed_batches`) | Отстаёт ли читатель от опубликованного состояния: кэши, задержка видимости, старый указатель. 0 % значит, что читатель всегда видит то, что уже опубликовано |
| **Запрос: медиана / p95** | `t_end − t_start` всех успешных запросов | Сколько стоит один запрос: чтение указателя, метаданных, манифестов и данных |
| **Запрос: медиана первых → последних 10 %** | Медиана `t_end − t_start` по первым и по последним 10 % запросов (по времени начала) | Деградация чтения по мере накопления снимков и манифестов |
| **Фиксация: медиана первых → последних 10 %** | Медиана `t_commit − t_start_фиксации` по первым и последним 10 % фиксаций | Деградация записи: каждая фиксация переписывает `metadata.json` целиком, а он растёт с числом снимков |
| **Публикация указателя (hint), медиана** | `t_visible − t_commit` | Дополнительная задержка схемы `hint` на публикацию `version-hint.text`. Для `rest` всегда 0 |
| **Объектов / МБ в префиксе таблицы** | Число и суммарный размер объектов S3 под путём таблицы после прогона | Сколько файлов порождают частые фиксации (данные, манифесты, списки манифестов, версии метаданных). Это стоимость хранения и листинга |
| **Последний `metadata.json`, КБ** | Размер текущего `metadata.json` после последней фиксации | Его читает каждый запрос и переписывает каждая фиксация. Он растёт линейно с числом снимков, пока их не удаляют (`expire_snapshots`) |

## Как читать результат

- **Целостность** — «Несогласованных результатов» должно быть 0 в обеих схемах.
- **Ошибки** — смотреть виды под таблицей. Для `hint` ожидается редкая ошибка DuckDB `ETag on reading file ".../version-hint.text" was initially … and now it returned …`: указатель заменили между двумя HTTP-запросами чтения. Запрос падает явно, повтор проходит. Её частота растёт с частотой фиксаций.
- **Свежесть** — «Возраст данных» сравнивать с половиной интервала фиксаций. «Пропустившие видимый пакет» показывают, не отстаёт ли читатель сверх этого.
- **Деградация** — «первые → последние 10 %» по запросам и фиксациям плюс размер `metadata.json` и число объектов. Ни уплотнение файлов, ни удаление старых снимков стенд не делает, это показывает худший случай без обслуживания таблицы.

## Ограничения

- Локальный MinIO: задержки S3 у облачного хранилища выше и менее стабильны.
- Короткие прогоны (минуты): на горизонте часов и суток без обслуживания таблицы деградация будет сильнее.
- Маленькие пакеты (1000 строк) и простая таблица без партиций.
- REST-каталог — тестовая реализация `tabulario/iceberg-rest` с хранением в памяти; промышленные каталоги (Polaris, Nessie, Lakekeeper и др.) могут вести себя иначе, в том числе кэшировать.
- Один писатель: конкуренция нескольких писателей за одну таблицу здесь не проверяется.
- Телеметрия выключена: у MinIO `MINIO_CALLHOME_ENABLE=off` и `MINIO_UPDATE=off`, у pip отключена проверка версии, установка расширений DuckDB во время прогона запрещена (`autoinstall_known_extensions=false`).

### Что важно знать о схеме `hint`

Каталог есть в обеих схемах. Разница в том, через что **читатель** узнаёт текущую версию таблицы.

- **Читатели `hint`** используют файл `catalog/<таблица>.duckdb`. В нём одно представление поверх `iceberg_scan(<путь таблицы>)`. Файл создаётся один раз после первой фиксации и во время прогона не меняется. Новую версию читатель находит через `version-hint.text`, который DuckDB читает при каждом запросе.
- **Писатель `hint`** фиксирует изменения через SQLite-каталог PyIceberg (`SqlCatalog`, локальный файл в контейнере runner). Без каталога PyIceberg не умеет атомарно переключить указатель на новый `metadata.json`. Читатели этот каталог не видят и доступа к нему не имеют. После каждой фиксации писатель публикует `version-hint.text` условной записью по ETag.
- **В `rest`** один REST-каталог служит и писателю, и читателям.

Писательская сторона в обеих схемах одинакова: каталог плюс атомарная фиксация. Схема `hint` добавляет только публикацию указателя.

### Выводы

1. **Целостность полная в обеих схемах.** Ни один запрос не увидел полусобранную версию, дубли или пропуски.
2. **Свежесть одинаковая и определяется только интервалом фиксаций.** Возраст данных в среднем около половины интервала: 0,5 с при стриминге и 5 с при микробатче. Ни одна схема не отставала от уже опубликованного состояния. Публикация hint добавляет около 2 мс.
3. **Скорость чтения одинаковая**, разница в пределах 1–2 мс. REST-каталог заметного выигрыша не даёт.
4. **Деградация одинаковая, её определяет число снимков, а не схема.**
   - За 180 фиксаций запрос замедлился примерно в 6 раз (11 → 65 мс), фиксация — в 2,5 раза.
   - За 60 фиксаций запрос замедлился примерно в 2,7 раза, фиксация — в 1,2–1,5 раза.
   - Причина: растёт число манифестов и `metadata.json`, а он переписывается при каждой фиксации.
   - Без уплотнения файлов и удаления старых снимков (`expire_snapshots`) частые фиксации непригодны на длинном горизонте в обеих схемах. При фиксации раз в секунду за сутки накопится около 86 тысяч снимков.
5. **Возможная кратковременная ошибка схемы `hint`.**
   - В этом прогоне ошибок не было.
   - В предыдущем похожем прогоне на этом же компьютере (тот же DuckDB, фиксация раз в 1 с и раз в 0,2 с) DuckDB изредка падал с ошибкой `ETag on reading file ".../version-hint.text" was initially … and now it returned …`. Это было 4 из 3000 и 19 из 2649 запросов.
   - Это гонка: hint заменили ровно между двумя HTTP-запросами чтения. Запрос падает явно, неверных данных нет, повтор сразу проходит.
   - Ровный ноль в одном прогоне не значит, что гонки нет. Клиенту схемы `hint` нужен автоматический повтор запроса при этой ошибке. У REST-каталога такой гонки по устройству быть не должно.
6. **Разница в объёме метаданных** (126 против 160 КБ) объясняется тем, что метаданные пишут разные реализации: PyIceberg в схеме `hint` и Java-сервер в `rest`. Принципиальной разницы схем она не показывает.

**Итог.** Для чтения при стриминге и микробатчах схема «`.duckdb` + hint» по целостности, свежести и скорости не уступает REST-каталогу. Её цена — редкая кратковременная ошибка при замене hint, которая лечится повтором запроса. Общее ограничение обеих схем — накопление снимков, его решает только обслуживание таблиц.

Ограничения этих результатов перечислены в разделе «Ограничения» выше. Главные: локальный MinIO, прогоны длиной в минуты и один писатель.
